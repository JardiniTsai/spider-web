# spider-web-zh：先定框，再展開，最後交給 grill-me

## 0. 只能明確呼叫（鎖）

- 只有使用者明確寫出 spider-web-zh（例如 `$spider-web-zh`、「用 spider-web-zh」、「跑 spider-web-zh」）時才啟動。
- 「幫我想幾個方向」「發散一下」「腦力激盪」這類說法**不得**啟動。可以問一句「要不要用 spider-web-zh 跑？」，但不得自行開始。
- 簡單任務（改短一封信、修一個錯字）直接做，不提 spider-web-zh。
- **唯一例外：回網換枝的重新進入**。使用者明確啟動過的那次流程，在拷問階段觸發 §8 換枝出口時，使用者或 agent 可以重新叫 spider-web-zh，但只能帶著既有的 `handoff.md` 和 `web.md` 進入「換枝模式」，不得開新題目。
- 若環境支援 `agents/openai.yaml`，其中 `allow_implicit_invocation: false` 也是這把鎖的一部分。

## 1. 流程總覽

```
明確呼叫 spider-web-zh
  → 階段 1：定框拷問（spider-web-zh 自己照 grilling 的問法跑，最多 5 題，只問題目）
  → 階段 2：骨架網（全部列出 → 分群，不刪；上限 30 個節點）
  → 階段 3：使用者圈選要深挖的節點（上限 5 個）
  → 階段 4：深展開（只對圈選節點填 13 欄）
  → 階段 5：使用者選定分枝 → 產出 handoff.md
  → 階段 6：寫完交接檔後直接啟動 grill-me，只拷問選定路線（spider-web-zh 的交接附加規則同時生效，含一次換枝出口）
  → 使用者確認共識後才執行
```

- 每個階段結束時，用一句話告訴使用者：現在在哪個階段、下一步是什麼。
- 每次執行的檔案放在工作區的 `spider-web-runs/<YYYYMMDD>-<短題目>/`。階段 1 結束就建立資料夾並開始寫 `web.md`，之後每個階段都更新它；階段 5 再寫 `handoff.md`。
- 成本上限見 §9，任何階段都不得超過。

## 2. 階段 1：定框拷問

這個階段**不載入** grilling skill，由 spider-web-zh 自己照 grilling 的問法進行：

- 一次只問一題，等使用者回覆後才問下一題。
- 每一題都附上你的建議答案。
- 能從環境、檔案或工具查到的事實，自己查，不問使用者；只有決定才交給使用者。
- 共識確認前不動手做任何解法。

定框專屬規則：

- **題數**：最多 5 題（「框定 OK」的確認不算題數）。下列四個面向都有答案就停，不必問滿。使用者的原話已經回答的面向不再問。
- **只問題目，不問解法**。不得提出、比較或暗示任何解法。使用者主動提出解法時，記成「使用者的初始想法」，到階段 2 當一般節點，不當前提。
- **四個必問面向**：
  1. **真正要的結果**：用「然後呢」階梯（見下）往上爬，找到最高但仍可交付的那一層。
  2. **硬限制**：預算、時間、法規、技術、人力、品牌等不能動的條件。
  3. **不探索的範圍**：明確排除的方向。
  4. **成功怎麼衡量**：可觀察的指標或判斷方式，以及由誰判斷。
- **「然後呢」階梯**：
  - 從使用者原本的說法開始，反覆問「做完這件事之後，然後呢？」，每次往上一層寫出更高的結果。
  - 每爬一層就評估能不能交付：在硬限制內，AI 加上現有資源，或可合理補上的工具／權限／資料，能不能在合理時間內交出成果？需要補的列進「需要的工具／權限／環境」，不因此直接退回一層。
  - 遇到第一個「做不好或太空泛」的層級（例如「幫我賺一百萬」）就**退回一層**，那一層就是「真正要的結果」。
  - 由你提出階梯草稿和建議停在哪一層，由使用者決定。
  - 創作類題目（作品風格、文案調性等）往上爬的效果有限：爬一層即可，或經使用者同意略過，直接記「真正要的結果＝原題目」。
- **產出「框定卡」**，最多 10 行：
  ```
  題目（原話）：
  真正要的結果（第 N 層）：
  被退回的上一層與原因：
  硬限制：
  不探索：
  成功衡量：
  使用者的初始想法（若有，當節點用）：
  ```
- **關卡**：使用者回「框定 OK」或修正後，才進入階段 2。

## 3. 階段 2：骨架網

- 在框定卡範圍內廣度優先展開，軸線包括高度、深度、廣度（跨領域）、速度（同樣的事做得更快，優先度最低）、需求、通路、變現、留存、生命週期，以及題目需要的其他軸線。
- **名詞換動詞（必做）**：展開前先把題目裡的成品名詞改寫成它要發揮的作用（例如「網站首頁」→「五秒內讓陌生人停下來並產生好奇」）。用這個作用問「全世界哪些行業最擅長這件事？」，至少找 3 個不同行業，各借一個手法，各成為一個節點。也可以問「這件事非成不可時，要組哪些專業的團隊？」來找行業，至少放一個對抗角色（例如放空研究員、鑑識會計師）。借的是那個行業實際的做法，不是模仿它的口吻。骨架網開頭要顯示這句動詞改寫。
- **不合理目標（可選）**：可以對某一群做一次，把成功指標設成不合理的極端值，問「如果這絕對做得到，做法會完全不同在哪？」，產出新節點。極端目標不得寫進框定卡的成功衡量，也不得當成承諾。
- **每個節點只寫三樣**：

  | 欄位 | 內容 |
  |---|---|
  | 名稱 | 短名，6–15 字 |
  | 一句話 | 這個節點是什麼、和其他節點差在哪，30 字內 |
  | 需求證據強度 | 強／中／弱／無，加一句依據（例如「有公開搜尋量」「只是推測」） |

- 需求證據只能小量查證：每個節點最多一次快速查詢，或用已知事實。不做深研究。
- **停止條件**：達到 30 個節點，或新點子都只是既有節點的小變化，先到者為準。因上限停止時，另列「還有的方向」最多 3 條，只寫名稱，不編號、不算節點。
- **輸出順序**：
  1. 完整節點清單：編號 N1、N2…，全部列出，不排序。
  2. 分群：每群列出所屬節點編號，不隱藏、不刪除、不合併節點。
  3. 標出明顯重複的節點，但仍然保留。
- 本階段**不推薦、不排序**。

## 4. 階段 3：使用者圈選

- 請使用者圈出要深展開的節點，最多 5 個；組合算 1 個。想圈更多時，要先刪掉別的。
- 這時可以給**一則**建議並附理由（例如「建議圈 N3、N7、N12」）。整張網已經可見，所以不算提早收斂。
- 使用者可以要求補一輪骨架（只能 1 輪），補完後節點總數仍不得超過 30。

## 5. 階段 4：深展開

- 只對圈選節點填完整 13 欄：更高層的結果、需求證據、第一批使用者、可重複的獲客管道、產品帶動成長循環、商業模式、留存路徑、專家方法、原始資料、外部驗證、跨領域手法、風險、需要的工具／權限／環境。
- 事實、工具和可行性自己查，每個節點最多 3 次查詢；查不到就標「未驗證」，之後放進 handoff.md 的未驗證假設。
- **「不適用」規則**：
  - 非產品題（內部流程、個人任務、一次性專案等）或節點本身不適用時，可以寫 `不適用：<一句理由>`。
  - **以下 5 欄不得標不適用**：更高層的結果、專家方法、原始資料、外部驗證、風險。任何題目都要填出實質內容。
  - 產品題中，若獲客、成長循環、商業模式、留存這 4 欄有超過一半標不適用，要在節點尾端註明「此節點可能不是產品機會」。
- **專家方法用深度四問填**：這個領域最頂尖的專家會做哪些我沒想到的事？會從哪些最原始、還沒被消化過的材料開始？用什麼方法和工具？除了你和我之外，什麼能證明結果是對的？
- **挑戰既有認知**：框定卡或使用者說法中的因果假設（例如「流失是新手引導的問題」），若有原始資料可查，就試著用原始資料重現或推翻，結果寫進「原始資料」欄；查不到就列為未驗證假設。
- **不合理目標壓力測試**：每個圈選節點至少做一次，寫成「極端目標下的做法」一段。
- **實體世界完整性**：節點若依賴真實世界的機制，要明列實體前置條件、需要的人或組織交接、時間延遲。範例資料、模擬、假串接或 demo 可以驗證介面或假設，但若繞過產品真正的實體機制，不得說成「已經完成啟用」。
- 結尾可以推薦節點或組合，並附理由。

## 6. 階段 5：選枝與交接檔

- 使用者選定一個分枝（一個節點或一組組合）並確認共識後，在同一資料夾寫 `handoff.md`，格式如下：

```markdown
# 交接檔：<題目短名>
- 日期：
- web.md：<路徑>
- 選定分枝：<節點編號與名稱；組合時列出各節點>
- 選定理由（使用者的原話或確認內容）：

## 框定卡
（原樣複製階段 1 的框定卡）

## 硬限制
- …

## 選定分枝的 13 欄
| 欄位 | 內容 | 證據強度（強／中／弱／未驗證） | 來源 |
|---|---|---|---|
| 更高層的結果 | | | |
| …（13 列，不適用要寫理由） | | | |

## 鄰近備案（最多 3 個）
| 節點 | 一句話 | 什麼情況下改選它 |
|---|---|---|

## 未驗證假設
| # | 假設 | 若為假的影響 | 驗證方法 | 需要使用者決定嗎 |
|---|---|---|---|---|

## 實體世界前置條件
| 前置條件 | 需要的交接（人／組織） | 預估時間延遲 | demo 能否代替（通常不能） |
|---|---|---|---|
（沒有的話寫「無實體機制」並附理由）

## 拷問狀態
- 回網換枝已用：否
- 已解決決策：（拷問中更新）
- 未解決決策：
```

- `web.md` 內容：框定卡、動詞改寫、完整骨架網、分群、圈選紀錄、深展開內容。

## 7. 階段 6：交給 grill-me

- 寫完交接檔後，直接啟動 `grill-me` skill，只拷問選定路線，照它的原文進行，不改寫、不省略它的任何規則。grilling 和 grill-me 的檔案一律不修改。
- 以下是 spider-web-zh 的**交接附加規則**，和 grill-me 同時生效（它們屬於 spider-web-zh，不屬於 grill-me；單獨使用 grilling 或 grill-me 時不適用）：
  1. 開始前先讀 `handoff.md`。交接檔已經回答的事實不重問；從「未驗證假設」和需要使用者決定的取捨開始。
  2. 每解決一個決策，就更新 `handoff.md` 的「拷問狀態」。
  3. 每一題都檢查是否觸發 §8 的換枝出口。
- 使用者確認共識後才可以執行。執行時照當下環境既有的交辦規則（例如把程式工作交給既有的工程流程或指定工具）。

## 8. 拷問的出口：回網換枝

- **觸發條件**（任一）：
  - 某個未驗證假設被證明為假，而且它是選定分枝成立的前提；
  - 拷問中出現和選定分枝不相容的硬限制；
  - 使用者表示框定卡的「真正要的結果」改變了。
- **重新進入**：停止 grill-me，由使用者或 agent 重新叫 spider-web-zh，帶著既有的 `handoff.md`、`web.md` 進入換枝模式（§0 的例外）。
- **換枝模式動作**：
  1. 說明哪個前提被推翻、證據是什麼。
  2. 回到 `web.md`，先看鄰近備案，再看其他已深展開或骨架節點；附建議提出 1 到 2 個替代分枝，由使用者選。提出前先逐條對照框定卡的硬限制，已知不相容的節點不提出。
  3. 新選的節點如果還沒深展開，就補做 13 欄，計入深展開 5 個的上限；上限已滿時，要請使用者先放棄一個已深展開的節點。
  4. 更新 `handoff.md`：「回網換枝已用」改成「是」，保留原分枝紀錄，改寫選定分枝相關各段。
  5. 再次直接啟動 grill-me，只拷問新選定路線；已解決而且仍然適用的決策沿用。
- **上限**：每次流程只能換一次。第二次再被推翻時，停下來回報使用者，建議重新定框或結束，不得自行再換。
- 如果被推翻的是框定卡本身（結果或硬限制改變），不算換枝，直接建議使用者重新明確呼叫 spider-web-zh，從階段 1 開始。

## 9. 成本上限

| 項目 | 上限 | 說明 |
|---|---|---|
| 定框拷問 | 5 題 | 四個面向都有答案就提早結束 |
| 骨架網節點 | 30 個 | 含補充輪；達到上限就停，另列「還有的方向」最多 3 條（只寫名稱） |
| 補充骨架 | 1 輪 | 使用者要求才做 |
| 深展開節點 | 5 個 | 組合算 1 個；換枝補做也計入 |
| 骨架需求查證 | 每節點最多 1 次快速查詢 | 深研究留到階段 4 |
| 深展開研究 | 每節點最多 3 次查詢 | 查不到標「未驗證」 |
| 回網換枝 | 1 次 | 見 §8 |

## 10. 發現 skill 缺陷時：只提案，不自己改

1. 發現缺漏的軸線、提早收斂或其他 skill 缺陷時，**不修改任何 skill 檔**（包括本檔、grilling、grill-me）。
2. 在當次回覆結尾附「修正提案」：問題、最小修正（用 diff 表示）、影響範圍、是否需要重跑。
3. 本次流程照現行 skill 繼續，除非使用者說要停。
4. 只有使用者明確核准提案後才改 skill，改完說明改了什麼。是否從原始 prompt 重跑由使用者決定，預設不重跑。
5. 不得把專案專屬的事實寫進這個通用 skill；需要時由使用者在呼叫前提供當次的專案背景。

## 11. 底線

- 不隱式啟動（§0 換枝重新進入除外）。
- 不超過 §9 的上限。
- 骨架網階段不排序、不合併、不推薦；分群不隱藏或刪除節點。
- 不丟一大份問卷給使用者，也不要求使用者自己想像所有可能。
- 能查的事實不問使用者。
- 不把 demo 或模擬說成真實世界的啟用。
- 使用者選定分枝並確認共識前，不執行。
